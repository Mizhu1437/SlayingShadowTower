## 一、P0 性能基准

### 1.1 运行方式

```bash
pnpm bench
```

### 1.2 测量方法（为什么可信）

前一版基准出现了**非单调数据**（2000 颗比 4000 颗还慢），根因是单次测量落在
`performance.now()` 噪声区。当前版本改用**时间累积法**：

| 措施 | 目的 |
| :--- | :--- |
| 每组累积 ≥120ms 再折算单次 | 把噪声占比压到 1% 以下 |
| 5 轮独立测量取中位数 | 抗离群值 |
| 每轮打乱执行顺序 | 消除 CPU 降频导致的系统性偏差 |
| 结束时做单调性自检 | **不单调就明确报告"数据不可信"，而不是继续用** |

### 1.3 结果：逐帧积分

SoA（`Float32Array` 并行数组，按需遍历） vs 对象数组

| 子弹数 | SoA 平均 | 对象平均 | SoA/对象 | 占预算 |
| ---: | ---: | ---: | ---: | ---: |
| 500 | 0.005 ms | 0.004 ms | 1.22x | 0.0% |
| 1000 | 0.010 ms | 0.008 ms | 1.16x | 0.1% |
| **2000** | **0.018 ms** | **0.015 ms** | **1.19x** | **0.1%** |
| 3000 | 0.026 ms | 0.022 ms | 1.19x | 0.2% |
| 4000 | 0.035 ms | 0.028 ms | 1.28x | 0.2% |

**单调性自检：✓ 全部通过**

### 1.4 结果：消弹碰撞

空间哈希 vs 暴力遍历（自机子弹 240 颗）

| 敌弹数 | 哈希平均 | 暴力平均 | 加速比 | 占预算 |
| ---: | ---: | ---: | ---: | ---: |
| 500 | 0.034 ms | 0.201 ms | **5.9x** | 0.2% |
| 1000 | 0.057 ms | 0.402 ms | **7.0x** | 0.3% |
| **2000** | **0.103 ms** | **0.805 ms** | **7.8x** | **0.6%** |
| 3000 | 0.149 ms | 1.208 ms | **8.1x** | 0.9% |
| 4000 | 0.197 ms | 1.575 ms | **8.0x** | 1.2% |

**单调性自检：✓ 全部通过**

### 1.5 结论

| 项 | 数值 |
| :--- | :--- |
| 2000 弹合计逻辑耗时 | **0.121 ms** |
| 一帧预算（60fps） | 16.667 ms |
| **占用** | **0.73%** |

> **逻辑层余量充足，性能瓶颈会在渲染侧。**

## 二、一个被数据推翻的假设（重要）

### 2.1 原假设

> 「子弹必须用 SoA（`Float32Array`）而不是对象数组，因为缓存局部性。」

### 2.2 实测结果

**2000 颗子弹：SoA 0.018ms，对象数组 0.015ms —— 对象数组反而快 1.19 倍。**

全规模区间（500–4000）都保持这个方向，且通过单调性自检，**不是测量误差**。

### 2.3 为什么假设是错的

| 原因 | 说明 |
| :--- | :--- |
| **V8 对「形状稳定」的小对象优化极好** | 同一构造函数、字段顺序固定的对象，V8 会分配连续内存并生成内联缓存 |
| **SoA 需要更长的遍历** | 即使做了 highWater 优化，仍有空洞需要跳过 |
| **对象数组只需一次数组遍历** | 数组本身连续，对象也是同形状的，实际行为接近 SoA |
| **工作量太小** | 4000 颗子弹只要 0.035ms，这个量级下缓存效应尚未成为主导因素 |

### 2.4 保留 SoA 的三条理由

即便如此，我**仍然保留 SoA 实现**，理由是：

| 理由 | 说明 |
| :--- | :--- |
| **渲染侧才是瓶颈** | 逻辑层 0.73% 预算，选哪个都不影响可行性 |
| **PixiJS 批量绘制需要并行数组** | 把 `Float32Array` 直接喂给顶点缓冲，不需要逐对象拷贝 |
| **可预测性** | SoA 的内存布局不依赖 V8 的对象优化策略，跨浏览器更稳 |

> **这不是"因为更快"，而是"因为更适合渲染管线"。**
> README 里**不能**写"用 SoA 因为缓存更快"——**实测不支持这个说法**。
