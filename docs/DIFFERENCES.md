## 〇、一句话概括

> **正作是「同一个武器变强」，本作是「换一种武器」。**
> **正作是「演奏」，本作是「组牌」。**

# 第一部分：设计差异

## 一、先说相同的（不回避）

这是二创，重叠是前提，不是缺点：

| 相同 | 说明 |
| :--- | :--- |
| 弹幕基础 | 判定点、决死 bomb、擦弹、慢速精确移动 |
| 按键骨架 | Z / X / Shift 的位置不变（但 Z 改作他用） |
| 关卡结构 | 道中 → 道中 BOSS → 关底 BOSS，四档难度 |
| 角色与世界观 | 东方 Project 的二次创作 |

评阅者看到「东方二创」，预期就是这些。

## 二、三个根本差异

### 差异 1：火力来源 —— 线性成长 vs 离散构筑

| | 东方正作 | 本作 |
| :--- | :--- | :--- |
| 怎么变强 | 吃 P 点，**数值线性上涨** | 拿符片，**形态离散变化** |
| 成长曲线 | 连续、可预测 | 跳变、每局不同 |
| 玩家的选择 | 几乎没有（只决定"吃不吃得到"） | 每一张卡都是选择 |

**正作里**：你的火力在第 30 秒和第 3 分钟是**同一个东西**，只是更粗。

**本作里**：你的火力可能是"三发追踪"，也可能是"单发穿透"，**取决于你拿了什么**。

> **正作是「同一个武器变强」，本作是「换一种武器」。**

### 差异 2：Z 键的性质 —— 维持 vs 决策

| | 东方正作 | 本作 |
| :--- | :--- | :--- |
| Z 键 | 按住射击 | **按下 = 打出一张卡** |
| 动作性质 | 维持（不产生决策） | 决策（何时、打哪张） |
| 手部负担 | 一根手指常压 | 指尖等待时机 |

**这是最实质的一处改动。**

正作里 Z 是"背景动作"——你从不需要想"要不要射击"，答案永远是"要"。本作把这个键位换成了**唯一需要主动决断的动作**。

**代价**：没有"纯躲弹"的纯粹感。
**收益**：每次按键都在做选择。

### 差异 3：局内的变化 —— 固定 vs 每局不同

| | 东方正作 | 本作 |
| :--- | :--- | :--- |
| 一局内 | 自机固定，火力单调上涨 | **构筑持续变化** |
| 关卡之间 | 结算，无交互 | **商店、交易、删卡** |
| 重开动力 | 打更高分、通关更高难度 | **试不同构筑** |
| 道中编排 | 固定 | **按种子随机生成** |

正作是"**演奏**"：同一首曲子，练到零失误。
本作是"**组牌**"：每次拿到的手牌都不一样，要找出一条能过关的路。

## 三、与《东方虹龙洞》的区分（最关键的一节）

虹龙洞（TH18）已有：**金钱 + 关卡间市场 + 能力卡改造火力**。
所以「有卡、有钱、有商店」本身**不构成创新**。真正的差别：

| 维度 | 虹龙洞 | 本作 |
| :--- | :--- | :--- |
| 卡的存在形式 | **永久被动改造**，买了就一直在身上 | **牌组**，抽/弃/过载循环 |
| 是否需要"打出去" | ❌ 不需要，自动生效 | ✅ 主动卡消耗能量打出 |
| 局内的卡牌操作 | **没有** | 手牌、抽牌、弃牌、过载 |
| 构筑的空间 | 买得起就买 | **卡池有限 + 可删卡** |
| 灵感来源 | — | 虹龙洞的被动卡 × 杀戮尖塔的牌组循环 |

> **虹龙洞是「关卡间的升级」，本作是「局内的牌组循环」。**

**这句话可以直接写进 README。** 它同时说明了灵感来源（诚实）与界限（有原创性）。

## 四、一张总表

| 维度 | 东方正作 | 虹龙洞 | 本作 |
| :--- | :--- | :--- | :--- |
| **射击** | 按住 Z | 按住 Z | **自动** |
| **Z 键** | 射击 | 射击 | **打出卡牌** |
| **火力成长** | P 点，数值 | 能力卡，数值 | **符片，形态** |
| **局内手牌** | ❌ | ❌ | ✅ 抽/弃/过载 |
| **能量** | ❌ | ❌ | ✅ 上限 3，每 5 秒 +1 |
| **关卡间** | 结算 | 市场买卡 | **商店 + 删卡 + 买命** |
| **道中编排** | 固定 | 固定 | **种子随机** |
| **构筑策略** | 无 | 弱 | **强（卡池 + 删卡）** |
| **重开动力** | 分数/难度 | 通关 | **试构筑** |

## 五、诚实的风险

| 风险 | 说明 |
| :--- | :--- |
| **纯 STG 玩家可能不满** | "为什么要我看手牌，我只想躲弹" |
| **认知负荷** | 躲弹 + 选卡 + 算能量，三件事同时进行 |
| **手感难以验证** | 卡牌 UI 会不会挡视线，只有实际玩过才知道 |

**第一条是设计取舍，不是缺陷。** 本项目做的不是正作，而是"用东方的皮包一个卡牌构筑游戏"。

# 第二部分：实现差异

> **前提说明：** 东方正作**未开源**。以下对比来自公开资料与社区逆向的一般认识，**非官方文档**。

## 一、技术栈层面

| 维度 | 东方正作（th06 以后） | 本项目 |
| :--- | :--- | :--- |
| **语言** | C++ | TypeScript |
| **执行** | 原生机器码 | JS 引擎（JIT 编译） |
| **图形 API** | DirectX 9（Windows 专用） | WebGL2（跨平台） |
| **输入** | Win32 消息循环 | 浏览器事件 + 手柄 API |
| **资源** | 打包进 `.dat` 归档 | JSON + 图片，构建时打包 |
| **平台** | Windows 独占 | 浏览器 + Windows exe |
| **内存管理** | 手动 / RAII | GC + **手动对象池** |

**最容易误解的一点**：语言不同 ≠ 能力不同。C++ 跑得快，但 JS 引擎的 JIT 在**数值密集的热循环**里性能可以接近原生。差别在于**能不能写出让 JIT 满意的代码**。

## 二、真正拉开差距的地方：数据与代码的边界

这一条比语言重要得多。

### 东方正作

弹幕行为、符卡编排、关卡波次，**多半内嵌在代码或私有脚本里**。要改一发子弹的角度，得改源码、重新编译。

### 本项目

```json
{
  "id": "spell_blue_moon",
  "duration": 22.0,
  "emitters": [
    { "t": 0.0, "count": 24, "angle": 0, "spread": 360,
      "speed": 220, "bullet": "rice_blue",
      "nested": { "interval": 0.5, "repeat": 40, "angle_step": 7 } }
  ]
}
```

**改一个数字，刷新页面就生效。** 不需要编译、不需要重启。

| 场景 | 正作方式 | 本项目方式 |
| :--- | :--- | :--- |
| 调符卡难度 | 改码 → 编译 → 运行 → 观察 | 改 JSON → 保存 → 页面自动刷新 |
| 单次迭代 | 几十秒到几分钟 | **约 1 秒** |
| 谁能改 | 只有会 C++ 的人 | **任何人** |

> **在 10 周左右的课程项目里，迭代速度比"我用 C++ 能写多快"更重要。**

## 三、最大的差异：可验证性

这是选择这个技术栈的**真正原因**，也是与正作最根本的不同。

| 项 | 东方正作 | 本项目 |
| :--- | :--- | :--- |
| 自动化测试 | 无（也没必要，有 bug 玩家会骂） | **vitest + Playwright** |
| 弹幕逻辑测试 | — | 无头跑，不启动浏览器 |
| 画面验证 | 人眼看 | **Playwright 截图 + 断言** |
| 性能基准 | 无公开数据 | **脚本输出 Markdown 表** |
| 回归保护 | 无 | 每次改完跑全量测试 |

**具体例子。** 手牌过载那条规则，可以写这样的测试：

```typescript
it('过载后重抽数量 = 初始手牌 + 本次抽牌', () => {
  const pile = new HandPile({ initial: 3, upper: 6, interval: 3 });
  pile.fill(6);                          // 手牌填满
  pile.drawEvent(1);                     // 触发抽 1
  expect(pile.size).toBe(4);             // 弃 6 抽 4
});

it('四种玩法抽牌量相同（中性验证）', () => {
  for (const behavior of ['hold', 'slow', 'normal', 'fast']) {
    expect(simulate(180, behavior).drawn).toBeCloseTo(60, 0);
  }
});
```

**第二条测试直接验证了「过载中性」这个数学性质。** 一旦有人（包括未来的 AI）改坏了规则，测试会立刻变红。

## 四、确定性与可复现

| 项 | 东方正作 | 本项目 |
| :--- | :--- | :--- |
| 随机源 | 内部实现，不公开 | **单一 Rng 实例，种子注入** |
| 能否复现一局 | 不确定是否有 replay | **能：种子 + 输入序列** |
| 出 bug 时 | "我打了半小时突然卡住" | **"种子 8842，第二幕 1 分 15 秒"** |

**做法是硬约束**：禁止 `Math.random()` 和 `Date.now()`，只能通过注入的 Rng。ESLint 规则强制检查。

### 4.1 结构化确定性（种子派生）

因为波次、掉落、商店全部按种子生成，必须做**结构化派生**：

```
masterSeed
  ├─ stage[act] = derive(masterSeed, "stage", act)   → 波次编排
  ├─ reward     = derive(masterSeed, "reward")       → 掉落与商店
  └─ cards      = derive(masterSeed, "cards")        → 抽牌堆洗牌
```

派生方式：`masterSeed + 标签` 哈希出子种子。**三个系统互不污染，且能单独重放任何一个。**

## 五、渲染与性能

| 项 | 东方正作 | 本项目 |
| :--- | :--- | :--- |
| 绘制方式 | DirectX 9 精灵贴图 | WebGL2 批量绘制 |
| 子弹实现 | 逐精灵绘制 | **结构化数组 + 一次批量提交** |
| 2000 弹 | 轻松 | 需优化，**这是真实风险** |

**三项必要优化（都有实测数据支撑）：**

1. **结构化数组**（`Float32Array`）而非对象数组 —— 缓存友好（空间局部性）
2. **对象池** —— 避免 GC 抖动造成的周期性卡顿
3. **空间哈希** —— 消弹碰撞从 O(M×N) 降到 O(M+N)

**P0 的第一件事就是那个 benchmark demo。** 如果实测顶不住，方案要调整——不假设它一定行。

## 六、分发

| 项 | 东方正作 | 本项目 |
| :--- | :--- | :--- |
| 渠道 | 同人展卖光盘 | GitHub + 构建产物 |
| 体积 | 约 300–500 MB（含 BGM） | 目标 **< 20 MB** |
| 更新 | 出新版本 | 刷新即最新（网页版） |

体积小是因为**零音视频素材**——全程序生成。这也是版权合规的副产品。

## 七、一句话总结

| 层次 | 结论 |
| :--- | :--- |
| **语言** | C++ vs TypeScript，但这不是关键 |
| **关键** | **内容全部数据化 + 全流程可自动化验证** |
| **代价** | 原生性能优势没了，靠算法和内存布局补 |
| **收益** | 迭代快约 50 倍，每个改动都有回归保护 |

> **正作是「一个人写一个引擎」，本项目是「用数据描述内容，用测试保证正确」。**

# 第三部分：对课程评分的落点

## 3.1 可以直接论证的两个改进（创新 10 分）

### ① 交互层面：把 Z 键从"维持"变成"决策"

> 论证：传统 STG 的射击是零决策动作，占用了玩家一只手和一份注意力。本作将其自动化，把该键位让给唯一需要决断的动作——出牌。**决策密度提高，操作负担下降。**

### ② 系统层面：把"火力成长"从数值改为形态

> 论证：正作的 P 点只改变数值，玩家在火力上没有选择。本作把火力拆解为可构筑的符片，使"变强"成为一个有取舍的决策过程。

## 3.2 五个可直接讲的技术判断（课程知识 30 分）

| 判断 | 对应的课程概念 |
| :--- | :--- |
| 子弹用 `Float32Array` 而非对象数组 | **空间局部性 / 缓存友好** |
| 消弹用空间哈希 | **时间复杂度 O(M×N) → O(M+N)** |
| 必须用对象池 | **GC 抖动对帧率的影响** |
| 随机只能单点注入 | **可复现性是测试的前提** |
| 内容全部数据化 | **迭代成本决定项目能走多远** |

**这五条覆盖了目标档要求的 9 个概念里的一半。**
